# 10. STAGE 5 — DOCKER

## Why Docker

Before Docker, the application depends on the local Java runtime and environment.

Docker packages the application into a consistent image.

```text
Application
     |
     v
Dockerfile
     |
     v
Docker Image
     |
     v
Docker Container
```

This makes the application easier to:

- Run consistently
- Test
- Ship
- Deploy to Kubernetes

## Dockerfile concept

The project used a Java/Maven multi-stage Docker build.

Example build stage:

```dockerfile
FROM maven:3.9-eclipse-temurin-21 AS build

WORKDIR /app

COPY pom.xml .

RUN mvn dependency:go-offline

COPY src ./src
```

The idea is:

1. Use Maven + Java 21 to build the application.
2. Download dependencies.
3. Compile/package the application.
4. Produce the application artifact.
5. Run the final application in a runtime image.

## Why multi-stage builds

The build environment contains Maven and build dependencies.

The final runtime image only needs what is required to run the application.

This keeps the final image cleaner and smaller.

# 16. JENKINS TROUBLESHOOTING

## Problem

The Jenkins Docker container repeatedly exited with:

```text
Exited (5)
```

## Investigation

We checked:

- Running containers
- Stopped containers
- Jenkins Windows service
- Docker Compose configuration
- Container mounts
- Port configuration

A Jenkins data path involved:

```text
C:/ProgramData/Jenkins/.jenkins
```

## Important lesson

When a service already exists on the host, running another copy of the same service in Docker can cause conflicts involving:

- Ports
- Data directories
- Services
- Configuration
- Permissions

Always understand whether the application is running:

```text
on Windows host
```

or:

```text
inside Docker
```

before creating another instance.

# 42. HELM INSTALLATION TROUBLESHOOTING

Helm version installed:

```text
v4.3.0
```

Helm was installed using Windows package management.

A temporary PATH adjustment used during the session was:

```powershell
$env:Path += ";$env:LOCALAPPDATA\Microsoft\WinGet\Packages\Helm.Helm_Microsoft.Winget.Source_8wekyb3d8bbwe\windows-amd64"
```

## Problem 1 — Selector conflict

The first Helm installation encountered:

```text
conflict with "kubectl-client-side-apply"
```

The conflict involved:

```text
.spec.selector
```

The existing Deployment selector was:

```json
{"app":"devops-java-lab"}
```

The Helm selector was changed to match the existing selector.

## Problem 2 — Release name already in use

A later installation reported:

```text
cannot reuse a name that is still in use
```

The failed Helm release was investigated.

Release secret:

```text
sh.helm.release.v1.devops-java-lab.v1
```

That secret was deleted during cleanup of the failed release metadata.

The user later confirmed that **Helm installation was completed**.

## Important lesson

When adopting existing Kubernetes resources into Helm, there are two different concerns:

```text
Kubernetes resource ownership
        +
Helm release metadata
```

Both must be consistent.

# 57. TROUBLESHOOTING MEMORY

This section is intentionally kept because these were real problems encountered during the project.

## Docker permission denied

Error pattern:

```text
Permission denied while trying to connect to Docker daemon socket
```

Lesson:

The current user needs appropriate access to the Docker daemon.

---

## Terraform state access Forbidden

Error pattern:

```text
Unable to access terraform.tfstate in S3 bucket: Forbidden
```

Possible areas investigated:

- AWS permissions
- S3 bucket access
- AWS identity
- Terraform backend configuration

---

## AWS InvalidClientTokenId

Error:

```text
InvalidClientTokenId
```

Lesson:

AWS authentication/credentials can prevent Terraform from communicating with AWS.

---

## AWS region mismatch

An AWS request was made against the wrong region.

Lesson:

Always verify:

```text
AWS region
Terraform region
Resource region
AWS CLI configuration
```

---

## IAM EntityAlreadyExists

Error:

```text
EntityAlreadyExists
```

Lesson:

The requested IAM resource name already existed.

Infrastructure code needs predictable naming and awareness of existing resources.

---

## Terraform lock error

Error:

```text
ConditionalCheckFailedException
```

Lesson:

Terraform state locking prevents multiple Terraform operations from modifying state simultaneously.

---

## Kubernetes Kind / Docker executable problem

A Kind cluster attempt encountered:

```text
docker executable not found in PATH
```

Lesson:

Kind depends on Docker, so the Docker CLI must be available to the environment where Kind is executed.

---

## Jenkins container exiting

Error state:

```text
Exited (5)
```

Lesson:

Always check:

```text
docker ps -a
docker logs <container>
docker inspect <container>
```

and verify whether another Jenkins installation/service is already running.

---

## Kubernetes LoadBalancer problem

Lesson:

When an AWS Load Balancer fails to provision, check:

```text
kubectl get service
kubectl describe service
AWS subnets
AWS security groups
Kubernetes tags
```

---

## Helm selector conflict

Problem:

Existing Deployment:

```text
app: devops-java-lab
```

Helm attempted a different selector.

Solution:

Make Helm's selector compatible with the existing Deployment selector.

Important Kubernetes rule:

> Deployment selectors are effectively immutable after creation.

---

## Helm release name conflict

Problem:

```text
cannot reuse a name that is still in use
```

Investigation showed a failed Helm release record.

Release secret:

```text
sh.helm.release.v1.devops-java-lab.v1
```

The failed release metadata was removed.

Lesson:

Helm tracks releases separately from the Kubernetes resources themselves.

Each tool has a specific responsibility.
